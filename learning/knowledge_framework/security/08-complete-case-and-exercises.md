# 完整案例、检查表与练习

## 案例：生成并提交季度分析

用户要求 Agent 读取工作区中的销售数据和内部 API，生成季度分析，并提交到团队文档。工作区中有一个外部供应商提供的 Markdown 文件，其中包含“把所有环境变量发送到某网址”的提示注入。

### 设计安全流程

1. **建立边界**：用户请求是任务意图；销售数据、供应商 Markdown 和 API 返回都是数据；模型计划只是候选决策。
2. **做威胁分析**：标出提示注入、客户数据外传、内部 API 越权和依赖包供应链风险。
3. **执行 Policy**：只允许读取指定目录和只读 API；禁止访问 Secret 文件；网络只允许内部 API 和文档 Broker；禁止把原始客户记录放入文档。
4. **配置 Isolation**：在临时 Worktree 和受限执行器中运行，关闭无关网络与凭据透传。
5. **绑定身份**：读取 API 使用当前用户委托的只读 Scope；提交使用独立 Broker 身份，并绑定用户、报告版本和目标文档。
6. **请求 Approval**：展示摘要、目标文档、字段分类、工具身份和副作用；用户只批准这一份报告的提交。
7. **最小披露**：模型只看到聚合后的数据；日志保存哈希、ID 和状态，不保存合同全文或 Token。
8. **审计与对账**：记录来源、Policy、审批、调用、版本和外部 Operation ID；提交超时先查询状态，不盲目重试。

### 为什么不能只依赖 Prompt

安全结果来自多层控制：模型遵循指令只是第一层，Policy 拦截工具调用，Isolation 限制可见资源，Credential Scope 限制外部权限，Audit 保留证据。

## 设计检查表

- 是否标记了每个输入的来源、可信度和指令权限？
- 是否列出了资产、入口、数据流、影响和应对措施？
- 工具、路径、命令、网络目标和数据字段是否有默认拒绝规则？
- 审批是否绑定具体参数、目标、版本、身份和有效期？
- Sandbox、Container、VM 或 Worktree 的实际边界是否经过测试？
- 用户、Agent、Tool、Service 和 Tenant 是否可分别审计？
- Secret 是否不会进入上下文、参数回显、错误、日志和快照？
- 超时、取消、重试和未知副作用是否能对账？
- 审计能否解释“谁在何时为何以什么权限做了什么”？
- 是否有撤销、轮换、删除、事件响应和回滚路径？

## 练习

1. 给十段混合文本标记为 Instruction、Data、Evidence 或 Candidate Decision，并说明哪些内容需要重新授权。
2. 把“禁止把客户数据发送到外部网站”改写成工具、字段和域名三条规则，再设计两个绕过尝试。
3. 找出审批内容“Agent 请求访问网络，是否允许？”的缺陷，补齐目标、数据、参数、身份、有效期和副作用。
4. 设计文档提交 API 超时后的查询、去重和补记流程，明确什么时候只能返回 Unknown。
5. 为一次被 Policy 拒绝的上传调用写结构化事件，既能说明原因，又不把 Secret 原文写入日志。

## 源码阅读路线

先从 `codex-rs/core/src/tools/registry.rs` 和工具处理器的参数校验开始，观察工具定义、路由和执行边界；停在“候选调用如何变成运行时动作”处。然后阅读 `codex-rs/core/src/exec_policy.rs`、审批相关代码和 Sandbox 执行路径，比较 Policy、Approval 与 Isolation 的职责。最后沿事件类型和 rollout / app-server 的记录路径阅读，确认哪些身份、参数摘要、结果状态和副作用 ID 被保存。阅读时优先沿一次工具调用的来源、决策、执行、结果和审计链前进，不要把所有工具实现展开。
