# Goal、成功标准与完成判定

## Goal 决定 Agent 为什么行动

Goal 描述期望达到的结果和边界。它应说明“要改变什么”，而不是提前锁死“具体怎么改”。

例如：

```text
较好的 Goal
    修复上传大文件时的内存溢出，同时保持现有行为不变。

过早限定方案
    把 upload.rs 第 42 行改成 8 KiB 的循环读取。
```

第二种写法可能恰好是正确方案，也可能忽略真正的内存增长点。Agent 应先围绕结果收集证据，再选择实现路径。

Goal 也不是一句无需验证的愿望。“优化性能”“做好报告”“解决问题”都缺少可观察的结果和边界。

## Success Criteria 把目标变成判断规则

Success Criteria 至少应回答四个问题：

1. 必须产生什么结果？
2. 哪些约束不能被破坏？
3. 用什么证据验收？
4. 哪些情况明确算失败或未完成？

```text
Goal
    上传大文件时不再耗尽内存。

Success Criteria
    1. 上传过程采用有界缓冲；
    2. 现有小文件行为保持不变；
    3. 相关自动化测试通过；
    4. 没有引入越权路径或未清理的临时文件。

Failure Criteria
    1. 仍需把整个文件载入内存；
    2. 只绕过测试而没有修复行为；
    3. 无法确认写操作是否产生重复副作用。
```

Success Criteria 可以来自用户、产品规范、协议、测试、合规规则和运行环境。它们可能有优先级，也可能互相冲突。Agent 需要保留来源，并在无法同时满足时请求澄清，而不是自行删除约束。

## 完成声明必须由证据支持

常见证据包括：

- 测试、断言、类型检查和静态分析；
- 文件、Diff、构建产物或外部资源状态；
- 数据查询、日志、指标和可复现结果；
- 有出处的引用或检索证据；
- 用户或领域专家的人工验收。

证据强度并不相同：

```text
模型推测“应该可以”
        < 工具返回“操作成功”
        < 重新读取真实状态
        < 独立测试或外部状态核对
        < 多种证据交叉验证
```

“模型说完成了”不是完成证据。“命令退出码为 0”也通常只能证明该命令成功，不能单独证明整个 Goal 已满足。

## Preconditions 与 Postconditions

每个关键动作都可以定义：

- Preconditions：动作执行前必须成立的条件；
- Postconditions：动作成功后应当成立的条件。

例如，修改配置文件前的 Preconditions 可以是“文件存在、版本未变化、当前路径可写”；Postconditions 可以是“配置可解析、目标字段已更新、其他字段保持不变”。

动作级 Postconditions 通过后，仍要回到 Task 级 Success Criteria。局部动作成功不等于全局目标完成。

## 谁可以改变成功标准

Plan 可以根据新证据调整，Success Criteria 不能被 Agent 悄悄放宽。需要改变时，应满足至少一种条件：

- 用户明确修改目标或接受范围变化；
- 上层策略或产品规则给出合法降级路径；
- 原标准事实上不可同时满足，Agent 说明冲突并请求决策。

预算不足、时间紧张或工具不可用，都不能自动把“未完成”改写为“完成”。Agent 可以返回部分结果，但必须明确哪些标准尚未满足。

## Goal 的层级

复杂系统可能同时存在多层 Goal：

```text
用户 Goal
    修复上传问题
        ↓
Task Goal
    找到内存增长点
        ↓
Action Goal
    读取并分析上传实现
```

下层目标必须服务于上层目标。若某个工具动作与当前 Task 有关，却不能推进任何 Success Criteria，就可能是无效探索。

## 本篇检查

面对一个 Goal，确认：

1. 它描述结果还是过早限定方案？
2. 成功、失败和不可违反的约束是否明确？
3. 每项标准由什么证据验证？
4. 标准的来源和优先级是什么？
5. 部分成功如何表达？
6. 谁有权改变验收边界？
