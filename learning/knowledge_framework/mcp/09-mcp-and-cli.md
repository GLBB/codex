# MCP 与 CLI：集成边界与选型

## 先明确比较对象

“CLI 与 MCP”至少可能指两个不同问题：

1. 用户通过 CLI、TUI 或 IDE 使用一个 Agent；
2. Agent 通过通用 Shell Tool 调用外部 CLI，或通过 MCP Client 调用 MCP Server。

第一个问题比较的是产品入口，第二个问题比较的是外部能力集成边界。本章讨论第二个问题。Codex 本身可以是 CLI 产品，同时作为 MCP Host 调用外部 MCP Server；两者并不冲突。

还要区分“由命令启动”和“通过 CLI 集成”。本地 stdio MCP Server 通常由 Host 执行一条带 `command` 和 `args` 的命令启动，但启动后双方交换的是 MCP JSON-RPC 消息。它仍是 MCP 集成，不是 Agent 自己拼接业务命令、读取 stdout 的 CLI 集成。

```text
CLI 集成
模型 → Shell Tool → 外部 CLI 子命令 → stdout / stderr

MCP 集成
模型 → Host 工具路由 → MCP Client → MCP Server → 结构化结果
```

## 两者解决的问题不同

CLI 是面向人、脚本和进程组合的命令界面。它通常提供子命令、选项、退出码、stdout 和 stderr，也可以选择输出 JSON 或 JSONL。Agent 经由 Shell Tool 使用 CLI 时，Host 主要约束进程和命令执行；命令内部包含哪些业务操作，未必具有独立的 Tool 标识。

MCP 是 Host 与外部能力提供方之间的互操作协议。它定义初始化、能力协商、Tool 与 Resource 发现、结构化调用、通知、取消，以及 Server 向 Client 发起的请求。Agent 通常不会直接生成 MCP JSON-RPC，而是由 Host 把 MCP Tool 转换为模型可见的工具，再将调用转发给 Server。

因此，CLI 的核心优势是复用和简洁，MCP 的核心优势是标准化的发现、交换和策略控制。二者都不能替代业务 API、Agent 循环或真正的操作系统安全边界。

## 对比维度

| 维度 | Agent 调用 CLI | Agent 调用 MCP |
| --- | --- | --- |
| 初始接入 | 已有稳定 CLI 时成本低 | 需要 MCP Server、Client 兼容和生命周期处理 |
| 能力发现 | 依赖 Skill、文档、`--help` 或自定义发现命令 | 原生支持 Tool、Resource、Prompt 列表及变更通知 |
| 参数 | Shell 参数或 stdin；结构和转义由调用方处理 | JSON Schema 描述的结构化参数 |
| 结果 | stdout、stderr、退出码；可约定 JSON / JSONL | Tool 调用结果、结构化内容、Resource 链接等协议结构 |
| 模型上下文 | 可只在需要时加载某个命令的说明 | 直接提供大量 Tool 定义时可能占用较多上下文 |
| Host 策略 | 常以整条命令、可执行文件和沙箱为边界 | 可按 Server、Tool、注解、配置和参数实施策略检查 |
| 交互 | stdin/stdout 约定，非交互运行时容易失效 | Elicitation 等能力具有明确的请求、关联和最终状态 |
| 复用 | 人、脚本和 CI 容易直接使用 | 不同 MCP Host 可以复用同一个 Server |
| 调试 | 终端中容易复现单条命令 | 能观察结构化生命周期，但需要协议日志或 Inspector |
| 主要风险 | Shell 注入、参数转义、文本解析、凭据出现在命令或日志中 | 工具投毒、能力定义膨胀、远程副作用、能力协商和授权错误 |

表中的优劣取决于具体实现。CLI 如果提供稳定的 JSON 输出、严格的参数验证和可靠的退出码，可以成为良好的 Agent 接口；MCP Server 如果提供规模过大的能力目录、返回无界文本或依赖不可信的描述，也不会自动变得可靠。

## 为什么有些集成从 MCP 改为 CLI

### 1. 复用已有的成熟产品接口

业务系统已经拥有稳定 CLI 时，认证、分页、重试、配置和错误处理可能都已实现。让 Skill 指导 Agent 调用现有命令，通常比维护另一套 MCP 适配器更简单。人也能在终端复现相同调用，有利于本地调试和自动化。

### 2. 减少静态工具目录

一个大型 MCP Server 可能提供几十甚至几百个 Tool。若 Host 把这些定义全部放入每一轮模型上下文，会增加 Token 消耗、降低缓存命中率，并扩大模型的选择范围。CLI 可以把能力组织成子命令，由 Skill 只在任务需要时提供相关用法。

这并不是 CLI 独有的优势。MCP Host 也可以使用允许列表、延迟发现、分页、Tool Search，或根据任务构建能力目录。真正需要关注的是“是否按需提供能力”，而不是“是否使用 MCP”。

### 3. 调用主要是本地、确定和一次性的

格式化文件、运行构建、查询本地状态等操作通常已经天然适合进程模型。若不需要远程多租户、动态发现、Resource、Elicitation 或长连接通知，引入完整协议层的收益可能有限。

### 4. 降低集成和版本维护成本

MCP 集成需要处理协议版本、能力协商、连接状态、超时、取消、能力目录变化和 Host 兼容性。当能力范围较小，并且只服务一个受控 Agent 时，维护 CLI 的成本可能更低。

这些原因只能说明 CLI 在特定约束下更合适，不能推出 CLI 普遍优于 MCP。一次迁移也可能是产品分发、认证体系、实现成熟度或团队维护能力的变化，而不是协议能力的排序。

## 什么时候优先选择 MCP

当同一能力需要被多个 Host 使用，或者需要动态发现、精细的 Tool 策略、结构化多媒体结果、Resource、Prompt、Elicitation、Sampling、进度和取消时，MCP 更适合这类需求。远程 SaaS、多租户身份和需要长期演进的公共集成，通常也更依赖稳定的协议边界。

选择 MCP 时仍要控制能力目录大小、结果上限和凭据；不要把“协议结构化”误认为“业务安全”。注解只是策略判断的参考信息，远程 Server 产生的真实副作用仍由外部授权、权限范围、审批和审计约束。

## 什么时候优先选择 CLI

当已有成熟 CLI、主要使用方是一个本地 Agent、操作容易用一次性进程表达，并且 Skill 能稳定约束命令和解析结构化输出时，CLI 往往更经济。开发工具链、构建系统和本地运维命令通常符合这些条件。

用于 Agent 的 CLI 最好提供：

- 稳定的非交互模式和机器可读 JSON / JSONL 输出；
- 明确且稳定的退出码与错误分类；
- 通过 stdin 或环境变量注入凭据，避免敏感值出现在命令行中；
- 为有副作用的命令提供幂等键、试运行（Dry Run）或可查询的操作 ID；
- 输出大小、等待时间和分页上限；
- `--help` 中清楚描述参数、默认值和副作用。

Host 还应限制可执行文件、子命令、工作目录、环境变量、网络和文件权限。仅在提示词中告诉模型“小心使用”，并不能形成真正的安全边界。

## 不应直接迁移的能力

从 MCP Tool 改成 CLI 子命令相对直接，但完整 MCP 不只包含 Tool。下列能力如果被压缩成一次普通 Shell 调用，往往会丢失语义：

- Resource 的 URI、订阅、寻址和缓存语义；
- Prompt 的发现和用户选择语义；
- Elicitation 的接受、拒绝、取消和请求关联；
- Sampling 的模型、Token、Tool 与嵌套预算控制；
- Progress、Cancellation、Logging 和实验性 Task 的生命周期；
- 动态能力目录变化，以及每个 Tool 独立的策略标识。

迁移前应逐项判断这些能力是否确实没有使用、能否由 Host 的其他机制承接，以及是否会退化成脆弱的文本约定。不能只验证“命令最终执行成功”。

## 选型路径

先确认能力的使用方和部署位置。如果它面向多个 Host、运行在远程服务中，或需要完整的 MCP 原语，应优先考虑 MCP；如果它已经是成熟的本地 CLI，并且只需要少量确定性操作，可以先验证 CLI 是否已经足够。

接着检查模型实际能够看到的能力范围。无论选择哪种方式，都只提供当前任务需要的能力：MCP 侧过滤能力目录，CLI 侧限制可执行文件和子命令。然后检查返回契约、凭据、审批、超时、取消、幂等和审计，最后使用真实 Host 测试从调用到结果回写的完整闭环。

```text
需要多 Host 互操作、动态发现或完整的 MCP 原语？
├── 是 → 优先 MCP
└── 否
    已有稳定、非交互、机器可读的 CLI？
    ├── 是 → 优先评估 CLI + Skill
    └── 否 → 比较两种对外接口契约的长期维护成本
```

## 共存通常比二选一更好

业务逻辑可以放在共享库或服务层，上层同时提供 CLI 适配器和 MCP 适配器。CLI 服务于用户、脚本、CI 和本地诊断；MCP 服务于支持该协议的 Agent Host。两种适配层共享认证核心、参数校验、幂等和结果类型，避免重复实现业务规则。

```text
                    共享领域服务
                    /              \
             CLI 适配器         MCP 适配器
           用户 / 脚本 / CI      Agent Host
```

采用这种结构后，迁移只需要调整能力的交付方式，而不必重写业务逻辑。是否同时维护两种适配器，应根据使用方数量和互操作收益决定；小型内部工具不必为了架构对称而增加第二个入口。

## 从 MCP 迁移到 CLI 的检查表

1. 列出原 Server 使用的 Tool、Resource、Prompt 和客户端原语，不要只统计 Tool。
2. 为每项能力标明使用方、调用频率、参数和返回结构、最大大小、副作用及授权方式。
3. 说明迁移目标：减少能力目录、复用现有 CLI、改善交付方式，还是停止维护 MCP 适配器。
4. 为 CLI 定义机器可读输出、错误分类、超时、取消、分页和版本兼容规则。
5. 映射原有的 Tool 审批、允许列表、凭据、来源追踪和审计能力，并记录无法等价映射的部分。
6. 对写操作验证幂等、结果状态未知和重试行为；对文本结果验证截断和提示词注入隔离。
7. 使用真实 Agent Host 比较迁移前后的任务成功率、Token、延迟、错误恢复和可观测性。
8. 只有在所有使用方完成迁移且不再依赖 MCP 特有语义后，才移除 MCP 入口。

判断迁移是否成功，不应只看代码量或单次调用延迟。更重要的是：能力是否仍可发现、调用是否仍受策略控制、结果是否仍可验证，以及失去的互操作能力是否确实不再需要。
