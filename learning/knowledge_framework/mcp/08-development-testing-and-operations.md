# MCP 开发、测试与运维

## 从选择协议原语开始

设计 Server 时，先判断“由谁控制、是否有副作用、是否需要寻址和缓存”，再选择合适的协议原语：

| 需求 | 建议设计 |
| --- | --- |
| 查询或改变业务系统 | Tool |
| 可寻址、可引用的数据 | Resource |
| 用户主动选择的领域模板 | Prompt |
| 缺少字段或需要用户确认 | Elicitation |
| Server 需要 Host 模型能力 | Sampling |

不要把所有能力都设计成 Tool。数据库 Schema 更适合通过 Resource 读取，查询操作更适合使用 Tool，引导用户完成分析的模板则更适合 Prompt。

## Tool 契约设计

高质量 Tool 应满足：

- 名称稳定、具体，并且在 Server 命名空间内唯一；
- 描述中说明适用条件、边界和主要副作用；
- 输入 Schema 严格限制类型、必填项、枚举值、长度和额外属性；
- 输出采用有界结构，必要时声明 `outputSchema`；
- 注解与实际行为一致；无法确定时采用保守描述；
- 写操作支持业务幂等键、预条件或可查询的操作 ID；
- 错误区分参数、认证、限流、暂时失败和业务拒绝。

不要在描述、Schema 默认值或错误消息中放入凭据，也不要依赖模型自行补全租户和权限边界。

## 选择传输方式

| 条件 | stdio | Streamable HTTP |
| --- | --- | --- |
| 部署 | 与 Host 同机子进程 | 独立远程服务 |
| 身份 | 进程与本地环境 | OAuth、Bearer、TLS、租户 |
| 扩缩容 | 通常按 Client 启动 | 可服务多个 Client |
| 主要风险 | 供应链、本地文件和环境变量 | 网络、认证、多租户和可用性 |
| 运维重点 | 进程退出、stderr、升级 | 负载、限流、重连、Token 轮换 |

传输方式属于部署决策，不应改变协议原语的业务语义。

## 测试分层

| 测试 | 验证重点 |
| --- | --- |
| Schema 与契约测试 | 能力定义、分页、调用结果与协议 Schema 一致 |
| 生命周期测试 | initialize、能力协商、通知、关闭和版本不兼容 |
| 传输测试 | 消息分帧、重连、stderr、HTTP、SSE 和认证 |
| Host 集成测试 | 能力目录、名称、审批、调用和结果回写闭环 |
| 外部系统集成测试 | OAuth、权限范围、限流、最终一致性和真实副作用 |
| 对抗性测试 | 工具投毒、提示词注入、巨型 Schema 和数据外传 |
| 恢复测试 | 超时、取消、崩溃、重复请求和结果状态未知 |

测试客户端或 MCP Inspector 可以验证协议行为，但不能替代真实 Host 中的工具目录、提示词优先级、策略和用户界面测试。

## 从原始协议过渡到 SDK 与 Inspector

手写 JSON-RPC 适合观察协议的主要调用链，但生产环境中的 Server 和 Client 应优先使用维护活跃且支持目标协议版本的 SDK。SDK 可以减少 Schema 类型、消息关联、能力声明、传输和升级兼容方面的重复错误，但不会自动解决业务授权、幂等、输出上限和提示词注入问题。

推荐开发循环：

```text
SDK 实现 Server
    ↓
MCP Inspector 检查连接与能力
    ↓
分别测试 Tool / Resource / Prompt / 通知
    ↓
真实 Host 验证能力目录、审批和上下文
    ↓
对接真实外部系统，验证身份、权限范围和副作用
```

使用 Inspector 时至少检查：

1. 初始化协商出的版本和能力是否符合预期；
2. Tool Schema、注解、结构化结果和业务错误能否正确展示；
3. Resource 的 MIME 类型、内容大小、模板和订阅是否正确；
4. Prompt 参数和生成的消息是否保留来源；
5. 列表变更、进度、日志等通知是否可以观察；
6. 非法参数、并发调用、断线和 Server 重启后的行为。

Inspector 只能证明 Server 提供的协议功能可以工作，不能证明某个 Agent Host 会把所有能力都提供给模型，也不能证明审批、认证或外部副作用是安全的。

工具用法以官方 [MCP Inspector](https://modelcontextprotocol.io/docs/tools/inspector) 为准；选择 SDK 时检查官方 [SDK 列表](https://modelcontextprotocol.io/docs/sdk) 的语言、协议版本和维护等级，不要只按包名相似度安装第三方实现。

## 必测场景

1. Server 返回零个、大量、分页或动态变化的 Tool。
2. 两个 Server 的 Tool 名称冲突或清洗后相同。
3. 注解缺失、错误或互相矛盾。
4. Tool 返回巨型文本、无效结构、媒体或嵌入式 Resource。
5. 调用超时后外部系统实际成功，Host 不应盲目重试。
6. Elicitation 分别遇到接受、拒绝、取消、超时和轮次取消。
7. OAuth 过期、权限范围不足、用户切换和租户错配。
8. Server 在 Tool 调用结果或 Resource 中注入恶意指令。
9. Sampling 尝试超出 Token、Tool 或嵌套深度预算。
10. Server 崩溃并重连后，能力目录和旧句柄失效。

## 可观测性

至少记录：

- Server ID、传输方式、版本和能力；
- connect、initialize、list、call、read 操作的延迟和结果；
- 能力目录的条目数、缓存命中率和变化次数；
- Tool 调用成功、业务失败、协议失败、超时、取消和拒绝；
- 审批请求和决策，但不记录敏感参数；
- Elicitation / Sampling 的等待时长、预算和最终状态；
- 调用结果的原始大小、截断量和写入模型上下文的 Token 数；
- 外部操作 ID、幂等键和审计关联 ID。

指标标签不应直接包含用户输入、完整 URI、Token 或高基数参数。

## 版本与兼容

- 初始化时协商协议版本，不按 Server 名称猜测；
- 不要调用尚未协商对应能力的方法；
- 对未知字段保持兼容，对未知业务语义保持保守；
- 草案功能和实验性 Tasks 应使用显式功能开关；
- 能力定义变化时，应使缓存失效并重新进行安全审查；
- SDK 升级后，重新运行 Host 集成测试和对抗性测试。

## 综合练习：数据库 MCP Server

设计一个教学 Server：

```text
Resource  db://schemas/{schema}
          提供数据库 Schema

Prompt    analyze_table
          提供用户主动选择的分析模板

Tool      query_read_only
          执行受限参数化查询

Elicitation
          缺少数据范围时询问用户

Sampling  可选
          请求 Host 模型解释查询计划
```

然后沿执行链、数据链和信任链分别回答：谁选择数据、谁授权查询、凭据在哪里、结果如何截断、恶意单元格文本如何隔离、超时后怎样确认查询状态。能回答这些问题，才算真正理解 MCP 集成，而不只是会启动一个 Server。

完成设计后，先用 Inspector 分别调用 Resource、Prompt 和 Tool，再接入真实 Host。最后为缺少数据范围的调用增加 Elicitation：分别验证接受、拒绝、取消、超时和连接断开，确认所有待处理请求都有明确的最终状态。
