云端 Agent 的 Trace，应该怎样展示？

面向亿级用户的自研 Agent：用一次执行的真实证据，连接工程排障与算法复盘。

Codex 源码与本地实测同事 Java Demo 静态审阅DeepSeek Harness 对照OTel GenAI / Langfuse 官方资料

给决策者的结论

01

两种视图，共用一次执行身份

Hera/OTel 负责全链路、错误和时延。Langfuse 负责 Agent 步骤、模型输入输出、工具结果与评测。统一 session、turn、step、inference、tool-call ID 才能从一边跳到另一边。

02

模型请求边界才是准确度基准

会话 rollout 可以重建行为视图；它不是每次实际发给模型的请求原文。上下文裁剪、压缩、模态过滤、重试和 provider 适配都可能改变输入。

03

先控制内容量，再验证 Langfuse 容量

“亿级用户”不足以推断吞吐。关键变量是 turn/s、step/turn、原文大小与保留天数。全量保留低体积指标，原文按权限和样本策略采集；生产规模以压测决定。

建议决策：推进“工程链路 + 算法轨迹”双视图试点。自研 Agent 的目标是 Java 外层、Rust SDK 内层，通过同进程 FFI 调用、云端容器部署；设计 trace 不依赖现有 Rust demo。先选真实 bad case 打通同一 turn 的 Hera ↔ Langfuse 跳转、模型请求原文对账和脱敏。原文入 Langfuse、保留 14 天目前只是方案假设，需算法与平台共同评审；据实际负载决定采样和集群容量。对应可执行设计见技术方案。

证据级别：本报告区分“源码可证”“本机样本实测”“官方文档”和“设计建议”。尚未对自研 Agent 或生产 Langfuse 做性能测试。

需求如何落到展示

“trace”不是一个界面或一种文件。一次 turn 可同时产生通用遥测、算法轨迹、会话恢复记录与诊断证据；不同对象各有用途。

Codex 与 Langfuse：哪些经验可借鉴

机制查到的事实对自研 Agent 的启示
Codex 原生 OTel当前源码在 SessionTelemetry::record_responses 记录若干 gen_ai.usage.* token 字段；其余大量内部函数 spans 可形成细粒度链路。先定义操作边界和字段口径，避免把每个内部函数都导入算法视图。
持久化 session rollout用于会话恢复；live history 的工具输出会裁剪，进入模型前还会归一化。Langfuse Codex 插件在 Stop hook 读取 transcript，重建 turn、generation 和 tool。可做行为回放与离线补录，但“完整模型输入”需在最终请求边界单独验收。
Codex Rollout Trace显式开启的本地诊断 bundle，保存有序事件、payload 与归约图；源码说明它不自动上传遥测。可借鉴“先记事实、后归约”和原文引用。MVP 先覆盖模型请求、工具因果、压缩事件，复杂运行时图按真实需求增量建设。
本地 Langfuse 样本同一次 Codex turn，插件语义视图为 34 个节点，原生 OTel 为 16,586 个节点；两路 trace ID 不同，内容和时延口径也不同。分别治理采集量；统一关联 ID；不要把两路 token/成本相加。样本只说明当前配置的行为，不代表稳定倍率。
DeepSeek Harness（DSH）以权威 Session 事件为基础做投影；普通产品遥测与 Session 遥测使用独立 OTLP logs 通道。Session 遥测默认由新反馈触发，外发副本可脱敏，按 session / 格式版本 / event seq 去重；请求有 4 MB 上限，交接不保证送达。借鉴“权威事件→受控投影”、通道隔离、大小上限和幂等键。DSH 的 Session OTLP logs 不是工程分布式 trace；其反馈门控策略也不应直接套用本项目。

源码基线：Codex 4bf76c22；DeepSeek Harness 639ed015；OpenTelemetry GenAI 本地固定 commit e57c543b。本地 34/16,586 样本来自此前 Codex 47d47812、Langfuse 4.46.0 的独立运行，见离线证据摘要与实验记录。Langfuse Codex 插件官方机制；DSH Session 遥测源码。

静态审阅 Java 仓库 98742947。这套 demo 已提供工程和算法两种信息，但算法内容来自独立的 debug 快照，并非 OTel span 自动包含。

亿级用户：容量问题怎样问

注册用户数不直接决定 Langfuse 性能。下式是规划工具，不是压测结果；带入实际 DAU、turn/人/日、每 turn observations、大小分布、峰均比与保留周期。

turns/day = 用户数 × DAU 占比 × 每 DAU 每日 turn
observations/day = turns/day × 每 turn 采集节点数
平均写入字节/秒 ≈ observations/day × 平均节点字节 / 86400
峰值 = 平均值 × 峰均比；留存量还需乘保留天数、复制与索引系数
仅作情景计算假设计算结果
10% DAU1 亿注册用户 × 10% DAU × 10 turn/日 × 30 节点/turn1 亿 turn/日；30 亿节点/日，平均约 3.47 万节点/秒
原始 payload平均每节点 2 KiB 或 20 KiB约 6.14 TB/日或 61.4 TB/日原始数据；未计压缩、复制、索引、多模态
内容重复多次模型调用重复携带长 prompt可能远超平均 20 KiB；须实测 p50/p95/p99 与大对象占比

Langfuse 官方说明其摄取采用 Web → 对象存储/队列 → Worker → ClickHouse，并建议在高负载下监测 worker 队列、拆分摄取与 UI、治理 ClickHouse 和对象存储。它支持 trace 级采样。上述能力说明可扩展路径，不能推导出本公司集群能承受目标吞吐。扩容文档 · 采样文档 · 保留策略及版本限制

本地 Compose 部署是功能验证环境，不用于生产容量结论。Langfuse 自托管的数据保留功能在官方文档中列为 Enterprise Edition；若使用 OSS，须单独设计生命周期并核对当前版本行为。

待确认事项与交付口径

算法要看什么

用 3–5 个真实 bad case 共同定义检视清单：最终模型请求、模型响应、工具因果、压缩/裁剪、检索材料、版本与评分。不要先假设“完整推理”可获得。

平台怎么接

确认 Hera 的 OTLP/采样/保留/深链能力，Langfuse 版本与权限能力，14 天清理方式及峰值负载。

Java ↔ Rust 边界

目标是同进程 FFI，Java 外层 Agent、Rust 内层 SDK。若使用 JDK 22+ 的 FFM API，可免写 JNI 桥接；仍需 Rust 导出 C ABI，并显式传递 trace context 与业务 ID。实现阶段确认 JDK 和 provider adapter 的归属。

“调研报告”和“技术方案”的关系：调研报告回答“现状是什么、证据支持什么、还有哪些未知”；技术方案回答“拟采用什么架构、怎样实施、何时算通过”。领导允许产出技术方案，通常表示可在调研结论之上提出可评审的落地路径。当前两份文件配套：本报告供理解和决策，技术方案供工程/算法/平台评审；后者的容量、权限参数仍须各方定案。
