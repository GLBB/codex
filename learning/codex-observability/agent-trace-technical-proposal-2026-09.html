Technical proposal · review draft · 2026.09.30

云端 Agent Trace 信息展示技术方案

用稳定的执行身份和受控的内容采集，形成工程排障与算法复盘可互相跳转的两个视图。

Java 外层 Agent + Rust 内层 SDK同进程 FFI 目标Hera + Langfuse14 天为待评审假设容量需实测
方案目录范围架构数据契约展示规模治理实施

1. 方案范围与原则

目标产品形态是 Java 外层 Agent、Rust 内层 SDK、同进程 FFI、云端容器部署，当前不计划使用 Agent 框架。设计 trace 不必等待已有 Rust demo。采集应从“谁要回答什么问题”出发：工程链路保留低体积事实；算法轨迹保留 Agent 行为；确切模型请求/响应是受权限保护的内容证据。

工程可观测

Hera 作为主入口

服务链路、时延分解、错误、依赖、日志和聚合指标。统一 traceparent，区分入口请求完成、turn 完成与模型流完成。

行为与质量

Langfuse 作为复盘入口

一 turn 一 trace；多 turn 组成 session；agent、generation、tool、retrieval 各为清晰节点。关联反馈、版本、实验和评测。

高敏证据

模型原文有条件采集

“模型原文可进入 Langfuse、保留 14 天”是当前待评审假设。先按授权样本采集完整原文，长内容可另存受控对象存储并留引用。Hera 不承载长 prompt。

推荐一期范围：一个线上灰度 Agent、文本 turn、模型调用、工具调用、上下文裁剪/压缩标记和一次失败样本。先建立准确性与权限基线，再扩到多模态、子 Agent 和大规模评测。采集比例、14 天保留及原文范围由算法、平台和数据负责人评审后定案。

2. 目标架构

Java Agent + Rust SDKJava 负责入口/turn 与编排；Rust 在其实际拥有的模型/工具执行边界记录事件
→
采集层 / 投影服务统一 ID、脱敏、采样、大小上限、异步批量、重试、幂等、丢失计数
→
Hera 工程视图OTLP spans + logs + metrics；trace ID 深链与告警
→ Langfuse 算法视图样本级 agent / generation / tool observations；模型、用量、输入输出投影、评分
→ 受控内容存储确切请求/响应与大工具结果；引用、版本、hash、拟定 14 天 TTL、权限审计

逻辑架构：采集层可以先由 Agent 埋点 + OTel Collector + 小型适配器组成，是否需要独立事件总线取决于峰值、补录与必达要求。Hera 与 Langfuse 需确认接口和权限后才能给出最终部署图。

Java ↔ Rust 关联约定：Java 创建 session_id/turn_id 和入口 span，同进程 native 调用时把 W3C traceparent/tracestate 及业务 ID 作为版本化参数显式传入 Rust；Rust 提取为 parent context 后建子 span。不能假设 Java 的线程局部 OTel context 自动跨语言。Rust 若拥有 provider adapter，就在最终出站边界捕获请求/响应；Java 负责最终用户 turn 输出与业务结果。Java 22 起正式提供 java.lang.foreign FFM API，可调用 Rust 暴露的 C ABI，免去 JNI 桥接；是否采用由目标 JDK、native ABI、回调/内存生命周期和性能验证决定。JDK 22 官方文档。

通道写入时机与载荷故障策略查询入口
低体积 metricsturn 结果、时延分布、模型/工具用量、采集丢失；全量聚合，低基数维度缓冲与告警；不依赖 Langfuse 采样Hera 看板/告警
工程 OTel trace请求/turn/step/模型/工具/存储/网络 spans；不写用户原文异步批量；限额、采样、错误优先；不可阻塞用户主链路Hera 瀑布图
行为 observations对一条完整 turn 做语义投影；模型输入输出在授权样本中可保留原文有界缓冲/重试、稳定 ID 去重；显式标记部分缺失Langfuse session/trace
原始内容证据在 provider 适配完成后、真正发送前捕获请求；流完成/失败时捕获返回与错误按策略落 Langfuse 或受控存储；上传失败留下缺失原因；限制单对象大小Langfuse 或权限控制的内部证据页

Java/Rust 均可使用各自原生 OTel API，经 OTLP/HTTP 导入 Langfuse；显式 langfuse.observation.type、langfuse.observation.model.name、langfuse.observation.usage_details 可避免仅靠名称猜测类型。官方映射和v4 迁移说明应按部署版本复核。同一模型调用只保留一个计量来源，不把 Hera 与 Langfuse 统计相加。

3. 最小数据契约

先固定对象与 ID，再选工具。业务 ID 不依赖 OTel span ID 生成；跨服务传递 traceparent，跨重试保留逻辑 inference ID 并增加 attempt ID。

对象 / 字段含义与约束主展示
tenant_id / user_ref租户和脱敏用户引用；用户原始 ID 不进 metrics 标签，不暴露给跨租户查询两侧筛选（受权限控制）
session_id / turn_id多轮与单轮身份；一个 turn 对应一个算法 trace；长期操作可另建 task/run IDLangfuse session/trace，Hera 可检索属性
trace_id / span_idW3C OTel 执行链路；Hera 深链。若 Langfuse 另生成 trace ID，建立显式映射表/链接Hera 链路与跨页跳转
step_id / step_indexAgent 一次决策步骤的稳定身份与顺序；允许重试、并发、子 Agent，用 parent ID 表因果算法时间线
inference_id / attempt_id逻辑模型调用与实际网络尝试分开；记录 provider、model、参数、usage、TTFT、结束原因和错误generation + 工程 model span
tool_call_id / parent_inference_id把模型发出的调用、执行和返给模型的结果连成一条因果链；输出可有截断版本tool 详情与工程依赖 span
content_ref / content_hash / capture_stage原文对象引用、完整性校验及阶段：context-built / before-send / after-receive / model-visible；明确是否脱敏或截断授权内容页与 Langfuse 元数据
prompt_version / agent_version / policy_version解释同一输入为何行为变化；包含工具目录或配置快照 hash算法过滤与实验对比

准确性要求：“完整模型输入”定义为 provider adapter 实际出站的逻辑 request（含 system/developer/user、历史、工具定义、模态引用、参数），并记录任何 wire 层再加工。单纯读取 session rollout 或上下文构建快照只可标为“重建视图/预发送快照”。响应只记录 provider 实际返回的字段；隐藏推理不可凭空生成。

推荐的最小事件序列

事件时间点与必要内容
turn.started / turn.finished入口、终局、失败/取消/超时、业务结果
context.prepared / context.compacted上下文版本、裁剪方式、前后 token/长度、来源引用
inference.requested / inference.completed最终请求引用、attempt、model、参数、首 token、结束原因、usage、响应引用
tool.requested / tool.completed调用 ID、参数引用、结果引用、重试/错误、是否最终传回模型
feedback.recorded显式反馈、任务结果、评测得分与评测版本

OpenTelemetry GenAI 规范仍处 Development。采用其 operation/model/usage 等语义，但把业务 ID、采集阶段、权限等字段放到公司自己的版本化 schema；升级语义规范时由适配层转换。规范及大内容建议。

4. 展示设计：从告警走到证据

Hera 页面

工程链路

按 turn 展示入口→Agent→模型/工具→存储的瀑布图；摘要含总时延、排队、TTFT、失败阶段、重试、用量。节点提供“打开算法轨迹”深链。

Langfuse 页面

算法轨迹

Session 列表按版本/模型/结果筛选；Turn 页展示 user→step→generation→tool→answer，支持比较上下文、输出、token、反馈，并跳转 Hera。

受控详情

模型输入与输出

按 system/developer/history/tool schema/模态组织请求；展示采集阶段、是否裁剪、内容 hash、授权状态与原文引用。只显示确实返回的 reasoning summary。

典型操作用户应看到验收方式
工程师从 p99 告警打开慢 turn瓶颈属于模型首 token、工具等待还是编排；可跳转对应 generation与服务端计时点逐项对账
算法同学复盘工具选择异常模型当时输入、输出的 tool call、工具参数/结果、下一次模型输入与同一 attempt 的请求/响应原文及 tool call ID 对账
压缩后回答偏离压缩事件、前后上下文 hash/长度、实际下一次模型请求选一个已知裁剪样本复核缺失信息
跨版本质量回归prompt/agent/model 版本、用户反馈、评测样本链接同一数据集上的版本对比，评分来源可追溯

算法检视的分层清单

层级建议记录回答的问题
每次模型调用的低体积事实模型/参数/版本、请求与响应时间、token、错误、结束原因、上下文长度、裁剪/压缩标记、内容可用状态哪个版本、哪一步、哪种输入结构发生了异常？
授权样本的完整模型可见内容实际出站 system/developer/user/history、工具 schema、多模态引用；返回的文本、显式 reasoning summary、tool call ID/参数、工具结果及下一次模型输入模型当时具备哪些证据，做了什么可观察的决定？
坏例/评测的附加标签用户反馈、任务成功标准、人工标注、评测器版本、预期行为和原始证据引用这次决策为什么被认为好或坏，改版后是否改善？

“模型为什么这么决策”在观测层只能解释可见输入、显式输出和后续结果的关系；未返回的隐藏推理不能还原。是否要对全部用户保存完整原文，应由算法团队以真实坏例收益与 14 天成本共同决定。

Langfuse 的推荐结构是 observation → trace → session；命名、层级和输入输出会影响检索、看板和评测。官方最佳实践。在 OTLP 路径上，需把 sessionId、userId、版本、标签等筛选字段传播到各 span，不能只放根节点。官方属性映射。

5. 高流量与高敏内容治理

控制项建议起点验收证据
采样全量低体积 metrics；工程 trace 采用有界比例并保留错误/慢样本；算法原文只采授权灰度、反馈坏例、指定调试样本。以完整 turn 为采样边界，跨节点一致。各层采样率、实际进入量、坏例保留率与上下文完整率
大小控制定义 span 属性、单条 observation、单次内容对象上限；大 prompt、长工具结果和多模态存储原文引用及 preview，记录截断标识。p50/p95/p99 payload、最大值、拒绝/截断率
脱敏和权限采集前剔除密钥/PII；内容读取按租户、角色和案例授权，保留审计。算法试验环境也不默认开放全部生产原文。脱敏样本检查、越权用例、访问审计和删除演练
异步与可靠性主链路只做有界内存操作，异步批量上报；队列满时按优先级降级并记录丢失；需要事后重放的通道增加持久化投递与幂等键。Agent 延迟开销、队列积压、端到端可见延迟、重试重复率
保留算法投影和原文暂按 14 天作为待评审假设；工程 trace、metrics 的保留期另与 Hera 确认。对象存储与索引同步删除。Langfuse 自托管内建保留能力按实际许可核实；如不可用，另设计经验证的清理机制。若 14 天获批，第 15 天不可从任何入口读回过期原文；保留/删除作业记录及跨系统一致性核对
租户隔离服务端代持 Langfuse 凭据；采集网关做身份、配额和项目路由；高基数字段避免作为指标标签。跨租户查询隔离、限流、配额与故障注入

容量估算输入：DAU、turn/DAU/日、模型调用/turn、工具调用/turn、每 turn 工程 span 数、每类 payload 分位数、峰均比、多模态占比、保留天数、抽样率。以这些值计算两条通道的 observations/s、MB/s、对象存储/天和查询负载，并用真实数据回放压测。不能从“亿级用户”或单机本地测试直接推出生产规格。

官方依据：Langfuse 扩容、trace 级采样、内容脱敏、保留策略；OTel 大内容建议外置存储并在 span 记录引用。

6. 分阶段实施和通过标准

P0 · 契约和样本
选 3–5 个真实案例，确认算法最小检视清单、内容权限、Hera 接口、目标 JDK 与 FFI ABI、负载基线；冻结 ID 与事件 schema v1。DSH 对照已完成静态审阅。
通过：每个案例的“问题→证据→需要展示字段”明确，所有字段有采集来源与 owner。
P1 · 单 Agent 试点
Java 与 Rust 在各自拥有的执行边界埋 span；在实际 provider 边界捕获；双向深链；Langfuse 语义投影；内容脱敏与授权读取。
通过：成功、工具失败、模型超时、上下文压缩四类样本逐项对账；跨语言父子关系、token 和尝试次数无重复；未授权用户读不到原文。
P2 · 灰度与容量
对代表性流量做采样、队列、worker、ClickHouse、对象存储和查询压测；观察 Agent 主链路开销与拟定 14 天删除。
通过：按公司 SLO 固定摄取成功率、可见延迟 p95/p99、丢失/重复率、查询时延、容量成本和恢复时间；门槛数值由平台确认。
P3 · 扩展
增加多模态引用、子 Agent 因果关系、反馈/评分与评测数据集；只有真实诊断案例要求时才扩展完整运行时图。
通过：新增类型都具备来源、权限、采样和回归案例，能够跨版本比较质量。

需要评审确定的五个决策

  1. 算法团队：具体要复盘的 bad case 和“完整输入/输出”的验收定义；按样本还是全量采原文。
  2. 平台团队：Hera 的 OTLP、trace 深链、采样、日志关联与容量接口。
  3. 数据/安全负责人：模型原文入 Langfuse 和 14 天保留是否采纳，是否包含 system prompt、工具结果和多模态，以及访问角色/删除流程。
  4. 业务负责人：DAU、峰值 turn/s、服务 SLO 与容量预算。
  5. 研发负责人：目标 JDK、FFM/JNI 选择、Rust C ABI、各层观测 owner。

当前状态：这是可评审的条件式技术方案，不是已验证的生产容量承诺。14 天与原文入 Langfuse 是待讨论假设；未取得自研 Agent 真实流量、Hera 能力清单和内容范围前，不宜固定采样比例或机器规格。DeepSeek Harness 的经验是“权威事件、投影、独立队列和幂等”，其 Session OTLP logs 与本方案的工程 trace 用途不同。进度与剩余工作见工作台，事实和证据见调研报告。DSH 参考。
