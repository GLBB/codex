# Agent Trace 信息展示调研：最终成果大纲

按此大纲形成的[文字稿](manuscript.md)与[最终 HTML 交付物](index.html)已放在同一目录。HTML 的案例交互使用合成数据，真实接入与容量的证据边界沿用正文说明。

## 定位与写作原则

本调研服务于**规划中的自研 Agent**：确定工程和算法两类 trace 应展示什么、需要记录什么、如何关联，以及 Langfuse 能否承载预期数据量。Codex rollout 是研究样本，用来检验数据结构和转换方法；它不是自研 Agent 已有的实现或必须照搬的协议。

最终成果用一条 Agent 执行案例贯穿。每个关键结论标明属于 **Codex 中观察到的事实**、**自研 Agent 的设计建议**，还是**需要在目标环境验证的假设**。展示效果、数据来源和采集位置应能相互对应。

## 正文大纲

### 1. 目标：两类 trace 分别回答什么问题

- 工程侧 OTel trace 服务于工程迭代：定位耗时、错误、重试、跨语言和跨服务调用。
- 算法侧 Agent trace 服务于算法迭代：回看模型实际获得的信息、行动选择、工具结果、最终产物和任务质量。
- 用同一案例说明两侧视图的读者、典型问题及共同的业务身份。

### 2. 工程侧：一轮 Agent 执行的 OTel trace 由哪些 Span 组成

研究对象是**自研 Agent 一轮执行的整条工程 trace**。本章先给出 Span 树，再说明树上每类 Span 的作用和属性。[GenAI 语义约定可视化的「Span 定义」页](../gen_ai.html)用于核对具体节点的标准名称和字段，不作为本章的组织顺序。

#### 2.1 主链路的 Span 树

- 从入口请求到 `invoke_agent`，再到每轮 `app.agent.step` 下的模型调用、工具执行和最终回答，画出父子关系与执行边界。
- 明确模型重试对应逻辑模型 Span 下的多次请求尝试；模型调用与后续工具执行在 Step 下是兄弟节点，不把工具耗时算进模型调用。
- 给出一条可读的成功链路和一条有错误或重试的链路，说明工程视图实际会显示哪些节点。

#### 2.2 按执行阶段说明每个 Span

- 按入口、Agent、Step、模型、工具、下游依赖的执行顺序，逐项给出 Span 名称与 kind、父节点、开始/结束边界、主要属性，以及它回答的工程问题。
- 在基本链路上按功能增加会话历史、检索、长期记忆、MCP、上下文压缩、子 Agent 或工作流节点；标明哪些是首期主链路，哪些只在对应功能发生时出现。
- 解释本地工具与 MCP 工具、逻辑模型调用与 HTTP 尝试、Agent 调用与子 Agent 执行的边界，避免同一个操作出现语义重复的 Span。

#### 2.3 Span 属性和语义约定对照

- 将每个实际节点映射到 OTel GenAI、MCP 或通用 HTTP/RPC/DB 约定；列出 `gen_ai.operation.name`、模型/工具/Agent 身份、token 用量、错误和调用关联键等关键属性。
- 对每个字段标明标准或自定义、必填或条件必填或推荐，以及缺失时会影响哪种查询或展示；provider 特化只在使用对应服务时说明。
- 将规范要求与本项目的采集要求分列；标准中的推荐字段可以因本项目的诊断需要成为项目必填。
- 对 Step、上下文压缩等自定义 Span 明确命名和属性；标准尚未定义的操作单独标注。记录所依据的 GenAI 约定版本与稳定度。

本章的主要产出是一张**自研 Agent 工程 trace 的 Span 树**和一张**树上节点的属性对照表**。瀑布图、跨服务传播和埋点实施作为解释树为何能用于排障的补充。

### 3. 算法侧：从 Session 历史到 Langfuse 展示

这一章保留三个小节，按**原始记录 → 语义节点 → 平台展示**逐步展开，避免把 rollout item、Agent trace 节点和 Langfuse observation 混为一谈。

#### 3.1 Session 数据契约：需要记录什么

- 定义 Session、Turn、Step 的范围，并以 Codex rollout 为参考梳理 item 类型。
- 列出关键字段：业务与调用身份、顺序和时间、角色与内容、模型请求/响应、工具调用/结果、上下文变化、用量、错误及终结状态。
- 指出哪些字段由自研 Agent 在运行时产生，哪些内容可能只保留摘要、引用或缺失；明确后者对诊断结论的影响。
- 区分实际传输请求、上下文处理后的有效上下文快照和历史重建视图；增量协议保留 delta、前序响应身份及恢复完整性。

#### 3.2 转换规则：如何形成 Agent trace

- 说明 item 如何排序、配对并聚合为 Session → Turn → Agent/模型/工具节点。
- 说明模型重试、并行工具、子 Agent、异步操作和不完整历史如何处理。
- 用贯穿案例展示原始 item 到节点树的映射，保留每个节点的证据来源。
- 明确 Step 映射为普通 span observation，模型按尝试形成 Generation；逻辑模型调用用共同 invocation ID 聚合，工具保留发起尝试和执行身份。

#### 3.3 导入与展示：如何进入 Langfuse

- 给出节点类型、父子关系、输入输出、模型用量、版本和业务键到 Langfuse 的映射。
- 区分 exporter 基地址与直接 POST 路径，给出 v4 ingestion 标头、鉴权和内容编码规则。
- 说明导入路径、内容保存方式，以及从任务结果或评分下钻到模型输入与工具结果的阅读流程。
- 区分导出成功、平台接收、节点可见和内容完整；列出各层的验收证据。

### 4. 两类 trace 如何互查

- 说明 `session_id`、`turn_id`、调用 ID 与两侧平台 trace/span/observation ID 的不同职责。
- 明确 `app.agent.model_call_id` 与算法侧 `invocation_id` 保存相同业务值，列出两侧字段名映射。
- 展示工程 → 算法、算法 → 工程各一次查询；用重试案例解释一对多关系。
- 说明关联字段缺失、数据未导入、采样或过期时的显示与验证方式。正文保持简短，详细契约放在专项设计中。

### 5. Langfuse 架构与大规模承载能力

- 画出摄取、队列/处理、ClickHouse、对象存储和查询的主要数据路径，解释各层如何分担负载。
- 按请求峰值、每次节点数、正文大小、保留期和查询并发建立容量模型；单独考虑重复 context、重试及回补。
- 说明可能的瓶颈、扩容条件和需要测量的指标。架构可扩展是设计依据；目标部署是否达标以压测结果为准。

### 6. 贯穿案例、验证结果与结论

- 用同一合成案例列出 Session 记录、拟建工程 Span 和算法 observation 的对应关系；工程视图明确标为设计示意。
- 分别列出已由源码或文档核实的事实、已有设计、真实样本验收结果和剩余待验证项。
- 分别报告合成样本的本地投递验证、已有真实 trace 的查询结果及自研 Agent 的待验收项，注明样本身份、版本、数量和证据边界。
- 给出自研 Agent 首期采集、展示和接入的建议边界，以及后续验证顺序。

## 已有证据与待验收项

已有[验证摘要](../assets/agent-trace-verification.json)记录：插件 `0.4.0` 将合成 JSONL 转为 4 个 observations 并发送到本地模拟接收器；已有真实 Langfuse trace 查询得到 34 个 observations。前者未导入真实项目，后者是已有数据的读取。长文件实验另提供历史保存内容与实际请求不一致的证据。这些结果尚未组成同一次执行的工程与算法双向互查验收。

1. 用自研 Agent 的真实 Session 样本确认最小记录契约、顺序与完整性；实际请求和有效上下文分别核对。
2. 以 GenAI 快照 `e57c543b4889619eb2a05702471937db5119165d` 为本稿基线，确认目标埋点库与后端的字段兼容性。
3. 在目标环境用同一条含工具与重试的真实任务，跑通工程采集、历史转换、Langfuse 导入、页面阅读及双向互查。
4. 用目标部署和实际数据体积分布压测摄取、可见延迟、查询与保留期成本。
