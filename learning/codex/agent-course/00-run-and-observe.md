# 00 跑起来：先认识一个 Agent，而不是先读源码

## 这一课解决什么问题

第一次接触 Coding Agent，人很容易犯两个错误：把它看成“会调用命令的聊天机器人”，
或者一上来钻进几万行源码。更有效的方法是先把系统当成黑盒，观察一次任务经历了什么，
再逐层打开黑盒。

这一课结束时，你会得到一张“单次任务观察表”。以后每学一个模块，都往这张表上增加
解释，而不是重新迷路。

## 先建立直觉：Agent 像一名在受控工作台里的工程师

想象你请一名工程师完成“看看这个项目的 README 是做什么的”。他不会立刻回答，而会：

1. 接收目标并确认工作目录。
2. 查看文件列表。
3. 打开 README。
4. 根据新证据组织回答。
5. 把做过的动作和结果留下记录。

Coding Agent 也是这五步，只是“工程师”被拆成了几个软件部件：

```text
用户目标
  -> Agent 运行时保存状态
  -> 模型决定下一步
  -> 工具在权限边界内执行
  -> 结果返回模型
  -> 运行时把事件发给界面并持久化
```

模型不是整个 Agent。它更像“下一步决策器”；状态、工具、权限和记录系统共同决定这个
决策能不能安全地变成现实。

## 第一次观察：同一个动作有四种视角

假设模型决定执行 `ls`。这一个动作在系统中至少有四种表示：

| 视角 | 看到什么 | 为什么需要 |
| --- | --- | --- |
| 模型 | 一个工具 schema 和稍后的工具结果 | 继续推理 |
| 运行时 | call id、参数、handler、状态 | 正确路由和取消 |
| 用户界面 | “正在运行命令”和输出摘要 | 了解进度并审批 |
| 持久化/trace | 可回放的调用和结果 | 恢复、排障和评测 |

初学者常把这四种表示都叫“消息”，然后状态设计很快失控。本课程会逐步给它们准确名字。

## 动手实验：运行并记录，不急着解释

本仓库的 `justfile` 位于根目录，并自动把 Rust 命令切到 `codex-rs`。在仓库根目录运行：

```bash
pwd
git status --short
just --list
just codex --help
just exec --help
```

如果 `just` 未安装，可以运行 `cargo install just`。首次编译较慢不是 Agent 卡住，而是
Rust 构建成本。

准备一个贯穿全课程的任务：

```text
请查看当前目录有哪些文件，并告诉我 README 是做什么的。
```

你可以在自己的 Codex 环境中运行它；如果当前没有模型凭据，也可以观看一次已有运行
记录或手工模拟。重点不是成功答案，而是填写下面的表：

| 时刻 | 用户看见的事件 | Agent 可能在做什么 | 证据 |
| --- | --- | --- | --- |
| 接收任务 | 任务开始 | 创建或取得当前 turn | 界面/协议事件 |
| 决定查看目录 | 工具调用开始 | 模型输出 tool call | 工具名和参数 |
| 得到文件列表 | 工具调用完成 | 结果进入上下文 | stdout 摘要 |
| 读取 README | 第二次工具调用 | 根据观察调整动作 | 新 call id |
| 给出回答 | 文本增量和完成 | 满足停止条件 | final message |

不要写“它应该是这样”。只记录你实际观察到的事实，不确定的地方标 `?`。源码学习的
价值，就是逐步把问号换成有证据的解释。

## 建立八格观察法

以后每次追踪一条任务，都检查这八格：

1. 输入从 CLI、IDE 还是 API 进入？
2. 当前 thread/session/turn 保存了什么？
3. 模型这一轮实际看到了什么？
4. 模型为什么选择这个工具？
5. 工具经过了哪些权限和 sandbox？
6. 用户收到哪些开始、增量、完成或错误事件？
7. 哪些事实被持久化，能否恢复？
8. 出错时从哪个 trace 把整条链串起来？

这不是背诵题。它是一套排障方法：任何 Agent bug，最终都能定位到某一格的“输入、
状态、决策、动作或记录”与预期不一致。

## 常见误区

- “最终回答正确，系统就正确。” 工具可能做了多余或危险的副作用。
- “模型说它读过文件，所以它读过。” 只相信工具事件和持久化证据。
- “一条用户消息只调用一次模型。” 一个 turn 往往包含多轮模型与工具交替。
- “CLI 没输出就是没工作。” 编译、网络等待和工具执行需要不同的进度信号。

## 理解之后再对照 Codex

现在只把概念与入口对应，不要求逐行阅读：

- `codex-rs/core/src/thread_manager.rs` 管理 thread。
- `codex-rs/core/src/session/session.rs` 保存进程内 session 服务。
- `codex-rs/core/src/session/turn.rs` 运行一次 turn。
- `codex-rs/core/src/tools` 负责工具声明、路由和执行。
- `codex-rs/rollout-trace/README.md` 与 `codex-rs/otel/README.md` 解释记录和观测。

想看完整入口关系时，再读 [Codex Query 处理流程](../query-processing-flow.md)。先找到你在
实验中观察到的事件对应哪里，看到主链路后停止，不要横向扫描所有模块。

## 本课验收

不用看笔记，解释下面三个问题：

1. 为什么模型只是 Agent 的一部分？
2. 同一次工具调用为什么需要模型、运行时、UI 和持久化四种视角？
3. 如果回答错了，八格观察法会让你先检查哪些事实？

你的产出是一张填写过的观察表，而不是“读完了几个源码文件”。
